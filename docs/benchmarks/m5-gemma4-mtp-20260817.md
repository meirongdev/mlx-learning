# Gemma 4 26B-A4B + Google's MTP assistant on M5 — 2026-08-17

**Host**: Apple M5 (base), 32 GB, 153.6 GB/s, `iogpu.wired_limit_mb=26000`
**Server**: omlx 0.5.7
**Method**: `completion_tokens / wall-clock POST duration`, non-streaming — identical to
`src/mlx_learning/benchmark_cli.py`. **3 timed repeats per cell, median reported.**
Driver: `scripts/mtpbench.py`. Both sides measured in a settled state (see Methodology).

Closes the gap flagged in [`m5-qwen38-27b-mxfp4-mtp-20260817.md`](./m5-qwen38-27b-mxfp4-mtp-20260817.md):
the **−12%** that grounds the "never enable speculative decoding on these MoE models" rule
was measured on the **M2 Pro** (2026-08-01), but Gemma 4 is the model the **M5** deploys,
and it had never been measured there.

Base: `mlx-community/gemma-4-26B-A4B-it-qat-nvfp4` (15.13 GB resident).
Drafter: `mlx-community/gemma-4-26B-A4B-it-qat-assistant-nvfp4` (Google's own,
`model_type: gemma4_assistant`, 0.23 GB, `block_size=4` → **M=5** positions per verify).

## Headline

1. **The −12% does not reproduce on M5, but this is no blowout either: MTP is
   neutral on general text (−0.3 to −0.9%) and +21.5% on code.**
2. **The MoE union-of-experts penalty is real, and now quantified.** Each extra verified
   position costs **~4.9× more** on this A4B MoE than on the dense Qwen3.8-27B — on the
   same machine, same day. The structural argument in `performance.md` is confirmed.
3. **It wins anyway on code because Google's drafter is exceptionally good there** —
   3.31–3.39 accepted tokens/round (77–80%), well clear of the ~2.7 break-even. General
   text sits *at* the break-even and is therefore a coin flip run-to-run.

## 1. Verify cost: the MoE penalty, measured

With `speedup = tokens_per_round / c`, where `c` is the cost of one M-position verify
forward in units of one single-token decode step:

| cell | tokens/round | speedup | implied `c` |
|---|---:|---:|---:|
| general 512 | 2.57 | 0.991 | 2.59 |
| general 1024 | 2.63 | 0.997 | 2.64 |
| code 512 | 3.36 | 1.215 | 2.77 |
| code 1024 | 3.34 | 1.215 | 2.75 |

**`c ≈ 2.7`, so break-even is ~2.7 accepted tokens/round.** The model predicts individual
runs, not just medians — the general cells straddle break-even and behave accordingly:

| individual general run | tokens/round | tok/s | vs 38.6 bare | implied `c` |
|---|---:|---:|---:|---:|
| best | 2.88 | 41.57 | **+7.7%** | 2.67 |
| worst | 2.37 | 35.50 | **−8.1%** | 2.58 |

Same `c`, opposite sign, purely from draft luck. That is what "sitting at break-even"
looks like, and it is why a single general-text measurement of this configuration is
worthless.

### Against the dense model on the same machine

| Model | Engine path | M | `c` | Cost per *extra* position |
|---|---|---:|---:|---:|
| Qwen3.8-27B mxfp4 (**dense**) | `VLMBatchedEngine` | 4 | 1.26 | (1.26−1)/3 = **0.087** |
| gemma-4-26B-**A4B** (**MoE**) | `VLMBatchedEngine` | 5 | 2.70 | (2.70−1)/4 = **0.425** |

**Each additional verified position costs ~4.9× more on the MoE.** This is the
union-of-experts effect stated in [`../performance.md`](../performance.md) — verifying N
positions activates the union of experts across them, so the weight read grows with N
instead of staying at the per-token active set — now with a number attached, measured on
one machine on one day with one engine path.

So the rule's *reasoning* was right. What it got wrong was treating the penalty as
disqualifying: a drafter good enough to clear a 2.7-token bar still wins, and on code
Google's assistant clears it comfortably.

## 2. Why code and not general

Inverted from the Qwen3.8 dense result, where code was the *worst* workload:

| | Qwen3.8-27B + `MTP-mxfp4` | Gemma 4 + `assistant-nvfp4` |
|---|---:|---:|
| general, tokens/round | 2.41 | 2.63 |
| code, tokens/round | 1.89 | **3.34** |

Google's purpose-built assistant drafts this code prompt at 78% acceptance; Qwen's
single-layer MTP head manages 44% on the same prompt. Drafter quality, not the base model,
decides which workload benefits — so "MTP helps general text, hurts code" is a statement
about the Qwen drafter, not about speculation.

## 3. Versus the M2 Pro result

| | M2 Pro (2026-08-01) | M5 (this round) |
|---|---:|---:|
| Gemma 4 bare | 44.3 | 38.6–39.1 |
| Gemma 4 + MTP | 38.9 (**−12%**) | 38.3 general (**−0.6%**) / 47.4 code (**+21.5%**) |

**Treat the cross-machine delta as indicative, not controlled.** The M2 Pro run used
`mlx-bench` with its default prompt at 512 tokens; this round used `scripts/mtpbench.py`
with two defined prompts and 3 repeats. The general-text comparison (−12% → −0.6%) is the
closest to like-for-like, and the sign change is larger than the harness difference
plausibly explains — but M2 Pro was never measured on a code prompt, so the +21.5% has no
counterpart there. **Re-running this exact script on the M2 Pro would settle it and is the
obvious next step.**

## Methodology: the warm-up trap that nearly produced a wrong answer

The first bare pass, run immediately after a restart that evicted a 14.6 GB model and
loaded this 15.1 GB one, was **systematically depressed by 25–30%**:

| cell | first pass | settled control | error |
|---|---:|---:|---:|
| general 512 | 28.96 | 38.59 | −25% |
| general 1024 | 28.87 | 38.67 | −25% |
| code 512 | 27.37 | 39.05 | −30% |
| code 1024 | 38.40 | 38.87 | −1% |

Only the last cell reached steady state. Taken at face value, that pass would have made
MTP look like **+24% to +70% across the board** — a dramatic, publishable, and entirely
false result. The tell was internal inconsistency: bare `code/512` (27.37) and bare
`code/1024` (38.40) imply a ~10.7 s fixed per-request overhead for a 71-token prompt,
which is not physical.

`mtpbench.py`'s built-in warm-up is one short generation, which is **not enough for this
model after a model swap**. The fix used here: three throwaway 400-token generations
before timing, plus re-measuring any suspect cell in a separate invocation.

The Qwen3.8 round on the same day was checked against this failure mode and is clean —
its MTP `general/512` and `general/1024` cells imply `c` = 1.223 and 1.216, i.e. the
entire difference between them is explained by acceptance (2.16 vs 2.41) at constant
verify cost, which a warm-up drift would not produce.

**Rule of thumb going forward: after any model swap, discard a full pass before timing,
and reject any bare baseline whose cells disagree by more than a few percent — bare decode
on these machines is flat.**

```json
    }
  }

```

**The documented TurboQuant KV conflict did not apply.** Gemma 4 loads with
`turboquant_kv_bits=None` on this M5, so `vlm_mtp_enabled` was accepted without contest —
contrary to `AGENTS.md`, which said the conflict applies because "the default model uses"
TurboQuant KV. Neither model on this machine enables it. Whether the M2 Pro differs is
untested.

Left **off** at the end of this round; the machine is in its as-found state.

## Caveats

- One drafter, one base, one machine, two prompts. The +21.5% is a property of *this* code
  prompt at 78% acceptance; a different code workload with lower acceptance would land
  closer to neutral, and below 2.7 tokens/round it turns negative.
- `c` is treated as constant per model but drifts 2.59 → 2.77 between the general and code
  cells; break-even is good to roughly ±0.1.
- Nothing here tests DFlash or DiffusionGemma, the other two rejected methods. Their −19…
  −29% and −68% results stand and were not re-examined.
