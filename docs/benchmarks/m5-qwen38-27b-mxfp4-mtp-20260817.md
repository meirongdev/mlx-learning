# Qwen3.8-27B mxfp4 + MTP on M5 — 2026-08-17

**Host**: Apple M5 (base), 32 GB, 153.6 GB/s, `iogpu.wired_limit_mb=26000`
**Server**: omlx 0.5.7
**Method**: `completion_tokens / wall-clock POST duration`, non-streaming — identical to
`src/mlx_learning/benchmark_cli.py`. Warm-up (cold load + one decode) excluded.
**3 timed repeats per cell, median reported.** Driver: `scripts/mtpbench.py`.

Cross-machine replication of
[`m2pro-qwen38-27b-mxfp4-mtp-20260816.md`](./m2pro-qwen38-27b-mxfp4-mtp-20260816.md).
Same model (`mlx-community/Qwen3.8-27B-mxfp4`), same drafter
(`mlx-community/Qwen3.8-27B-MTP-mxfp4`), same omlx version, and — because both rounds
drive `scripts/mtpbench.py`, whose prompts are module-level constants — **the same two
prompts**. Unlike the round-1/round-2 comparison inside the M2 Pro report, the code cells
here are strictly apples-to-apples across machines.

## Headline

1. **MTP wins every cell on M5, including code.** +41% to +98%, where the same
   configuration on M2 Pro ranged from −4% to +11%. The documented "≥2.0 accepted
   tokens/round to break even" threshold is **M2 Pro-specific**; on M5 it is ~1.26.
2. **MTP inverts the machine ranking.** Bare, M2 Pro beats M5 by ~38% (bandwidth, as
   expected). With MTP, **M5 beats M2 Pro in every cell** — 16.75 vs 13.14 on the best.
3. **Acceptance is machine-independent; verify cost is not.** At identical tokens/round
   (2.41 on both machines, general/1024), M5 gains +98% and M2 Pro +11%. Draft quality is
   ruled out as the explanation, isolating the M=4 verify forward as the entire cause.

## 1. Every MTP cell wins, and code wins too

| cell | M5 bare | M5 + MTP | Δ | M2 Pro bare | M2 Pro + MTP | Δ |
|---|---:|---:|---:|---:|---:|---:|
| general 512 | 8.50 | 15.01 | **+76.6%** | 11.62 | 11.52 | −0.9% |
| general 1024 | 8.45 | 16.75 | **+98.2%** | 11.83 | 13.14 | +11.1% |
| code 512 | 8.49 | 12.09 | **+42.4%** | 11.48 | 11.23 | −2.2% |
| code 1024 | 8.50 | 11.98 | **+40.9%** | 11.75 | 11.30 | −3.8% |

The code cells are the important ones. On M2 Pro, code was where MTP turned into a net
loss, and that loss is what made the feature not worth enabling. On M5 the *same* draft
quality on the *same* prompt yields +41–42%.

## 2. Why: verify cost, isolated

With `block_size=3`, each MTP round runs one verify forward over M=4 positions and emits
`tpr` tokens; bare decode emits 1 token per forward. So

    speedup = tpr / c        where c = cost(M=4 verify) / cost(1 decode step)

Solving for `c` per cell:

| cell | tokens/round | speedup | implied `c` (M5) | implied `c` (M2 Pro) |
|---|---:|---:|---:|---:|
| general 512 | 2.16 | 1.766 | 1.22 | 2.16 |
| general 1024 | 2.41 | 1.982 | 1.22 | 2.17 |
| code 512 | 1.82 | 1.424 | 1.28 | 1.92 |
| code 1024 | 1.89 | 1.409 | 1.34 | 1.92 |

**M5's M=4 verify forward costs ~1.26 decode steps; M2 Pro's costs ~2.04** — a **1.6×**
relative advantage. Since break-even is `tpr = c`, the practical thresholds are:

| Machine | Break-even tokens/round |
|---|---:|
| M2 Pro | **~2.04** |
| M5 | **~1.26** |

Measured acceptance never dropped near 1.26 in any run, including the worst individual
code sample (tpr 1.77 → 11.06 tok/s, still +30% over bare). On M5 this drafter has no
losing workload in the tested set.

This is consistent with — and is much stronger evidence for — the existing hypothesis in
[`../performance.md`](../performance.md) that M5's GPU neural accelerators (Oct 2025)
explain its anomalous NVFP4 result. A batched M=4 verify is exactly the compute-dense,
bandwidth-light shape those units favour, while single-token decode is pure bandwidth,
where M5's 153.6 GB/s loses. omlx confirms it takes an M5-specific path at load:

    omlx.patches.qwen35_fa256_attention - Qwen FA-256 steel patch skipped: NAX GPU, stock SDPA is faster

## 3. Machine ranking inverts

| Config | M2 Pro | M5 | Winner |
|---|---:|---:|---|
| bare, best cell | **11.83** | 8.50 | M2 Pro, +39% |
| + MTP, best cell | 13.14 | **16.75** | M5, +27% |
| + MTP, code 1024 | 11.30 | **11.98** | M5, +6% |

"The older M2 Pro is faster" holds for plain decode and is restated correctly in
`AGENTS.md`. It does **not** survive enabling MTP on a dense model — M5 wins every cell
once speculation is on, despite 23% less bandwidth.

## Configuration

`vlm_mtp_enabled` is a **per-model** setting in `~/.omlx/model_settings.json`, not a key
in `settings.json`:

```json
{
  "version": 1,
  "models": {
    "mlx-community__Qwen3.8-27B-mxfp4": {
      "vlm_mtp_enabled": true,
      "vlm_mtp_draft_model": "mlx-community__Qwen3.8-27B-MTP-mxfp4"
    }
  }
}
```

Two traps:

- **Drafter attachment is fail-soft.** If the drafter fails to load, `engine_pool` logs a
  warning and serves bare — a benchmark would silently measure the baseline twice. Always
  confirm `VLM MTP enabled for <model>, drafter=<id>` and the presence of `vlm_mtp stats:`
  lines before trusting a number.
- **The documented TurboQuant KV conflict did not apply here.** `Qwen3.8-27B-mxfp4` loads
  with `turboquant_kv_bits=None`, so `vlm_mtp_enabled` was accepted without contest. The
  conflict in `AGENTS.md` is a property of the *default deployed model*, not of this one.

The admin endpoint `PUT /admin/api/models/{id}/settings` also sets this, but requires
admin auth (401 without it); writing the file and restarting is the scriptable path.

## Memory

The "does a dense 27B fit on a 32 GB M5" question resolved comfortably — **nothing needed
to be unloaded**:

| | |
|---|---|
| Weights resident | 14.64 GB bare / 14.85 GB with drafter |
| GPU wired limit | 26000 MB |
| Swap | 3.9 GB → 5.5 GB during load, settled back to ~5.3 GB |
| System free | steady 34% for the remainder of the run |

The swap excursion is a one-time load transient, not thrashing. Its only measurable effect
was on the first timed cell (see the baseline correction above) — which is a reason to
discard the first cell after a cold load, or warm harder before timing.

## Caveats

- One model family, one drafter, one engine path (`VLMBatchedEngine`, dense Qwen3.5-arch
  VLM). Whether M5's verify advantage generalizes to other dense models is untested.
- `c` is treated as constant per machine, but it drifts slightly upward on the code cells
  (1.22 → 1.34). KV length and prompt are confounded with it here; the break-even figures
  are good to roughly ±0.05, not more.
- Nothing here challenges the MoE result. The union-of-experts effect is structural and
  independent of verify-kernel efficiency.

## Follow-up this opens

**Re-test Gemma 4 + its own MTP assistant on M5.** The −12% that grounds the blanket "never
enable speculative decoding" rule was measured **on M2 Pro** (2026-08-01) — but Gemma 4 is
the model M5 *deploys*, and it was never re-measured there. If M5's verify forward is 1.6×
cheaper for this dense model, a −12% could plausibly land positive. The MoE
union-of-experts penalty still argues against it, so this is genuinely open rather than
predicted; it is cheap to test, since both checkpoints are already on the M5.
