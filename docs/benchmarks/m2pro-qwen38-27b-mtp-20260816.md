# Qwen3.8-27B (dense) + MTP on M2 Pro — 2026-08-16

**Host**: Apple M2 Pro, 32 GB, 200 GB/s, `iogpu.wired_limit_mb=30720`
**Server**: omlx 0.5.7 (restarted; the box had been serving from a 14-day-old 0.5.4rc1 process)
**Method**: `completion_tokens / wall-clock POST duration` — identical to
`src/mlx_learning/benchmark_cli.py`, so numbers are comparable to the figures in
[`../performance.md`](../performance.md).
Warm-up (cold load + one decode) excluded. 2–3 timed repeats per cell; median reported.

## Headline

**Nothing in the `mlx-community/qwen38` collection is a throughput upgrade for this
machine.** The best Qwen3.8-27B configuration reaches 14.29 tok/s against the current
Qwen3.6-35B-A3B MoE at **58.04 tok/s** — a **4.1× slowdown**. Adoption is a
capability-vs-speed trade, not an optimization.

**MTP works, but its payoff is workload-dependent and inverts on code.**

## MTP acceptance telemetry

omlx logs per-request MTP stats (`vlm_mtp stats: ... accepted=X/Y tokens_per_round=Z`),
which separates draft quality from verify cost. `block_size=3`.

| Workload | acceptance | tokens/round | net vs bare |
|---|---:|---:|---:|
| general, 1024 tok | 71.2% | 2.42 | **+28%** |
| general, 512 tok | 43–52% | 1.87–2.05 | **+12.5%** (nvfp4) |
| code, 512 tok | 41.4% | 1.83 | **−5%** |
| code, 1024 tok | 34.5% | 1.69 | **−10%** |

Payoff tracks acceptance rate, and acceptance tracks how *predictable* the text is —
not prompt type in the way one might guess. The high-acceptance 1024-token general case
is a "200-word" prompt stretched to 1024 tokens, so the tail is repetitive and trivially
draftable; treat +28% as an optimistic ceiling, not a representative figure. On code —
the actual reason to want this model — acceptance falls to 34–41% and **MTP is a net loss**.

The break-even is around 1.9–2.0 tokens/round: below it the M=4 verify forward costs more
than the forward passes it saves.

## Why affine `4bit` loses with MTP while `nvfp4` gains

The quant ranking **inverts** depending on whether MTP is on:

- bare: 4bit 11.24 > nvfp4 10.96 (affine +2.6%)
- with MTP: nvfp4 12.33 > 4bit 8.79 (affine **−29%**)

Acceptance was near-identical across the two (1.90 vs 2.00 tokens/round), so this is
verify cost, not draft quality.

omlx 0.5.7 ships `patches/qwen35_verify_qmm.py` — Metal kernels written specifically for
MTP verify shapes (M = 1 + draft depth), benchmarked by its author on Qwen3.6-27B, exactly
this model shape. It gates on affine quantization only:

```
qwen35_verify_qmm.py:41   Supported: 4-bit and 8-bit affine, group_size in {32, 64, 128}
qwen35_verify_qmm.py:470  getattr(self, "mode", "affine") == "affine"
```

That predicts affine `4bit` should win with MTP. **It does not, because the kernel never
arms for this model.** Two independent reasons, both verified:

1. The kernel is armed from `patches/mlx_lm_mtp/batch_generator.py::_call_backbone` — the
   **native `mtp_enabled`** path. The working path here is `vlm_mtp_enabled`, which
   bypasses mlx-lm's BatchGenerator entirely.
2. Native `mtp_enabled` is unreachable for this checkpoint anyway. omlx loads Qwen3.8-27B
   through `VLMBatchedEngine` (it is a VLM — `Qwen3_5ForConditionalGeneration` with a
   `vision_config`), and `patches/mlx_lm_mtp/qwen35_model.py:45` states the native patch is
   *"intentionally limited to `mlx_lm.models.qwen3_5`; mlx-vlm's `mlx_vlm.models.qwen3_5.language`
   is a separate copy and is not touched."*

Probing `mtp_enabled: true` directly confirms it, fail-soft and silent:

```
mlx-vlm runtime MTP patch applied for .../Qwen3.8-27B-4bit (config declares mtp heads
but checkpoint ships no mtp.* weights; MTPModule attachment skipped to keep strict
load_weights happy)
VLMBatchedEngine loaded: .../Qwen3.8-27B-4bit
```

Without the fast kernel, stock MLX `qmm` at M=4 is simply worse for affine group_size-64
than for nvfp4 group_size-16. **So on the only MTP path that works, pick `nvfp4`.**

### Merging the MTP head would not help

The base checkpoints declare `text_config.mtp_num_hidden_layers: 1` and
`mtp_use_dedicated_embeddings: false` but ship **zero** `mtp.*` tensors. The separate
`Qwen3.8-27B-MTP-*` repos (0.25–0.87 GB, `model_type: qwen3_5_mtp`, `block_size: 3`) contain
exactly the missing head, and their tensor names map 1:1 onto the native `MTPModule`
(`pre_fc_norm_hidden`, `pre_fc_norm_embedding`, `fc`, `layers.0.*`, `norm`) — so a
`mtp.`-prefixed merge looks tempting. It is a dead end: the VLM engine would still not run
the patched mlx-lm class, so the fast verify kernel stays unarmed regardless.

## Recommendation

Keep `Qwen3.6-35B-A3B-nvfp4` as the default. It is 4–5× faster and nothing here changes that.

Add Qwen3.8-27B only as a *second, deliberately-selected* model for work where its
capability jump matters (Terminal-Bench 2.1 63.4→73.0, DeepSWE 1.1 13.3→42.2,
OSWorld-Verified 63.9→84.3, plus native vision):

- **Coding / agentic → `Qwen3.8-27B-4bit`, MTP off.** 11.45 tok/s, the fastest config for
  low-predictability output. MTP is a net loss here.
- **General prose / high-redundancy output → `Qwen3.8-27B-nvfp4` + `MTP-nvfp4`.** 12.33–14.29 tok/s.

Enabling MTP also costs functionality: `vlm_mtp_enabled` is mutually exclusive with
TurboQuant KV, guided grammar, thinking budget and repetition penalties
(`omlx/model_settings.py:292-317`). The current default model uses `turboquant_kv_enabled`,
so this is not a setting to turn on globally.

Configuration used for the MTP runs (`~/.omlx/model_settings.json`, restored to `{}` after
testing; backup at `~/.omlx/model_settings.json.bak-20260816-pre-qwen38-mtp`):

```json
"mlx-community__Qwen3.8-27B-nvfp4": {
  "vlm_mtp_enabled": true,
  "vlm_mtp_draft_model": "mlx-community__Qwen3.8-27B-MTP-nvfp4"
}
```

Drafter repos are auto-detected as helpers (`model_discovery.py:97`,
`HELPER_CONFIG_MODEL_TYPE_SUFFIXES = ("_assistant", "_mtp")`) and stay hidden from
`/v1/models` given `hide_helper_models: true`.

## Relation to the existing MoE finding

[`../performance.md`](../performance.md) records that DFlash (−19/−29%), Gemma's MTP assistant (−12%) and DiffusionGemma
(−68%) all lost on this box, and attributes it to MoE expert-union reads, closing with:
*"Speculation beats the bandwidth limit is a dense-model rule and inverts here."*

This run tests that claim on an actual dense model. The rule is **half-confirmed**:
speculation does stop being structurally doomed — MTP produced a real +12–28% on general
text, which never happened on any MoE. But it is not a reliable win either. On a
bandwidth-bound Mac the M=4 verify forward is expensive enough that MTP needs roughly
≥2.0 tokens/round to break even, and code generation on this model delivers only 1.69–1.83.

Revised rule: **on dense models speculation can pay, but only above ~2.0 accepted
tokens/round — measure acceptance from `vlm_mtp stats` before trusting it.**
